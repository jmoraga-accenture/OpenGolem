Date: 2026-04-07
Audience: Development team
Author: Kai (coder)

## Comparison basis

This document compares the actual tagged releases:
- **v0.1.0** → commit `c5cdc28`
- **v0.3** → commit `c68d655`

For avoidance of doubt:
- current local `main` after documentation merge is **`e1bba88`**
- that `main` commit is **not** the subject of this runtime comparison
- all receipts below compare **`v0.1.0` vs `v0.3`** directly

## Scope

This is a **runtime-capability comparison**, not an architecture-compliance review.
The goal is to validate whether the reported operational losses are actually regressions in `v0.3` relative to `v0.1.0`.

Each item is classified as:
- **Regression confirmed**
- **Not a regression**
- **Improved in v0.3**
- **Inconclusive from static code**

---

## Executive summary

After comparing the release tags and validating the relevant functions/files, I do **not** find evidence that the following were lost in `v0.3`:
- writable workspace access
- persistent session state
- context compaction hook

The strongest correction is this:

> The "session resets when it gets too large" behavior was already present in `v0.1.0`.
> In fact, `v0.3` raises the threshold from **300 KB** to **10 MB**, which is an improvement, not a regression.

So the disciplined conclusion is:

- **No static-code evidence of a v0.3 regression** in writable workspace behavior
- **No static-code evidence of a v0.3 regression** in persistence/transience
- **No static-code evidence of a v0.3 regression** in context compaction existence
- **The continuity-clear behavior exists in both releases**, with a much more permissive threshold in v0.3

If there were real runtime failures in practice, they are **not explained by a simple v0.1.0 → v0.3 code regression in these areas**. They would need to come from:
- environment/configuration differences
- deployment/runtime bugs
- SDK behavior outside the compared host code
- operational breakage not visible in the static diff alone

## Claim-by-claim comparison

## 1) "Bots couldn't create files in their workspace"
**Verdict:** **Not a regression**

### v0.1.0 receipts
- `container/Dockerfile:52,67`
  - creates `/workspace/group`
  - `WORKDIR /workspace/group`
- `src/container-runner.ts:230-239` (v0.1.0)
  - mounts `groupDir -> /workspace/group`
  - `readonly: false`

### v0.3 receipts
- `container/Dockerfile:52,67`
  - same writable workspace structure
- `src/container-runner.ts:230-239` (v0.3)
  - same `groupDir -> /workspace/group`
  - same `readonly: false`

### Assessment
Writable group workspace exists in both releases.
The main project mount remains read-only by design (`/workspace/project`), but that is not new in v0.3.

### Dev-team conclusion
This is **not validated as a v0.3 regression**.
If agents failed to write files in practice, investigate:
- whether they targeted `/workspace/project` instead of `/workspace/group`
- container runtime mount failures
- permissions/ownership drift in deployed environments

## 3) "They were not compacting context"

### v0.1.0 receipts

  - `createPreCompactHook()` archives transcript before compaction
- `container/agent-runner/src/index.ts:500-503`
  - `PreCompact` hook registered with the SDK

### v0.3 receipts
- `container/agent-runner/src/index.ts:160-205`
  - same `createPreCompactHook()` behavior
- `container/agent-runner/src/index.ts:500-503`

If compaction failed in production, that is more likely:
- SDK behavior divergence
- hook not firing in a real edge case
- a runtime path outside the static happy path

But it is not absent from the code.

## 4) "They reset the session when context was too long"
**Verdict:** **Not a regression; improved in v0.3**

This is the most important correction.

### v0.1.0 receipts
- `src/index.ts:426-429`
  - comment explains large sessions caused repeated timeout behavior
- `src/index.ts:429`
  - `const MAX_SESSION_BYTES = 300_000;`
- `src/index.ts:443-449`
  - if session file exceeds threshold:
    - log warning
    - `delete sessions[group.folder]`
    - `deleteSession(group.folder)`

### v0.3 receipts
- `src/index.ts:484`
  - `const MAX_SESSION_BYTES = 10_000_000;`
- `src/index.ts:443-450`
  - same continuity-clear mechanism when threshold exceeded

### Assessment
The continuity-clear behavior is **not new** in v0.3.
It already existed in v0.1.0.
Moreover, the threshold increased from **300 KB** to **10 MB**, making v0.3 materially less aggressive.

### Dev-team conclusion
This item is **not** evidence of functionality loss from v0.1.0 to v0.3.
If anything, v0.3 improved tolerance before clearing state.

## What this means for the team

If users observed severe operational failures after updating to v0.3, those failures are **not explained by the specific code paths above as simple regressions from v0.1.0**.

The next places to investigate are:
1. **Deployment/runtime drift**
   - container runtime differences
   - mount failures
   - permissions mismatches
   - environment variables not matching expectations

2. **SDK/runtime behavior outside static host code**
   - compaction hook firing conditions
   - session file growth characteristics
   - resume behavior under real workloads

3. **Operational observability gaps**
   - missing logs around mount failures
   - lack of explicit telemetry for compaction events
   - insufficient reporting on why a session was cleared or failed to resume

---

## Recommended next engineering actions

### A1 — Instrument compaction and session-clear events
Add explicit audit/logging for:
- compaction hook fired
- archive written successfully
- session cleared due to size threshold
- stale-session clear reason

### A2 — Reproduce reported failures in a controlled environment
Create an integration script that verifies:
- file write to `/workspace/group`
- persistence across container restarts
- session resume across multiple turns
- PreCompact firing on long conversations
- behavior after large transcript growth

### A3 — Distinguish product failures from code regressions
If the reported runtime problems are reproducible, file them as:
- environment/runtime bugs
- SDK integration bugs
- observability gaps

not as "v0.3 removed persistence/compaction/workspace capability" unless new evidence appears.

## Bottom line

With receipts:

> The specific losses claimed here are **not validated as v0.3 regressions** versus `v0.1.0`.
> The strongest candidate — oversized session clearing — already existed in `v0.1.0`, and `v0.3` actually makes it less aggressive by raising the threshold from 300 KB to 10 MB.

That is the professional, evidence-backed conclusion from the code comparison.
