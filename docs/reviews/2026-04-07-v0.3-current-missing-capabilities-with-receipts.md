# OpenGolem — v0.3 Current Missing Capabilities (with receipts)

Date: 2026-04-07
Basis:
- `v0.3` tag → commit `c68d655`
- Survey of current v0.3 source tree and v0.3 docs/specs/security reviews

## Scope

This document answers a narrower and more accurate question than "what regressed from v0.1?"

It catalogs capabilities that are **still missing in v0.3** based on current receipts.
These are not all regressions from v0.1.0. Some are simply unfinished items in the v0.3 architecture/program plan.

---

## Executive summary

After correcting the earlier false positives, the strongest missing items I can still support in v0.3 are:

1. **Dashboard skill implementation is still missing**
2. **MCP `min_permission_tier` is parsed but not enforced at call time**
3. **Audit-log tamper-evidence is still Phase 2 only**
4. **Tier 3 strategic memory exists structurally, but real sqlite-vec semantic search/indexing is still incomplete**
5. **The human-calibration product surface is still incomplete because the dashboard is not shipped**

Everything below includes receipts.

---

## 1) Dashboard skill implementation is still missing
**Status:** Missing in v0.3

## Receipts
- `docs/ARCHITECTURE.md` status table:
  - `Governance / dashboard surface | Planned | M29–M32`
- `docs/PM_BRIEF.md`
  - `Phase 2 — Security & UX | K | UX — Report Dashboard | Not started`
- `docs/PLAN_V1.md`
  - dashboard work appears in M29/M30/M31/M32 as future work
- `docs/specs/dashboard-skill-spec.md`
  - normative spec exists
- expected implementation path in plan:
  - `src/skills/dashboard/`
- actual source survey:
  - no `src/skills/dashboard/` implementation present in `v0.3`

## Assessment
The project has moved beyond "dashboard idea" into a written spec, but the actual dashboard skill is still absent.

## Why it matters
This is not just nice-to-have UI.
The architecture repeatedly says human calibration depends on the dashboard surface.
So until it exists, one of the core governance loops is still incomplete in product terms.

---

## 2) MCP `min_permission_tier` is parsed but not enforced at call time
**Status:** Missing / deferred in v0.3

## Receipts
- `src/skills/skill-schema.ts`
  - parses and validates `mcp.servers[].min_permission_tier`
- `src/skills/skill-schema.test.ts`
  - tests schema rejection when `min_permission_tier` is absent
- `docs/DECISIONS.md` (Decision 29)
  - explicitly states enforcement is deferred to Phase 2
- `docs/security/stream-g-cybersecurity-report.md`
  - explicitly says call-time enforcement of `min_permission_tier` is deferred; in Phase 1 any user in a group with an MCP-declaring skill can trigger declared MCP endpoints regardless of permission tier

## Assessment
The schema field exists and is validated, but it is not yet a runtime authorization control.

## Why it matters
This is a real missing capability, not a documentation nit:
- the system can describe permission tiers
- but it cannot yet enforce them at invocation time

---

## 3) Audit-log tamper-evidence is still Phase 2 only
**Status:** Missing in v0.3

## Receipts
- `docs/DECISIONS.md`
  - per-writer HMAC audit chain is explicitly Phase 2
- `docs/security/stream-g-cybersecurity-report.md`
  - same conclusion; `hmac` column reserved, all Phase 1 writes set NULL
- `docs/specs/audit-log-spec.md`
  - `hmac TEXT` exists in schema, Phase 1 nullable
- `src/shared/audit/index.ts`
  - event schema includes optional `hmac?: string | null`
  - write path persists `params.hmac ?? null`

## Assessment
The audit system exists, but the stronger integrity property — tamper-evident chained entries — is not yet implemented.

## Why it matters
This leaves the governance story weaker than the philosophy suggests.
Cato and the dashboard/admin surfaces can only be as trustworthy as the audit log they read.

---

## 4) Tier 3 strategic memory is structurally present but real semantic/vector capability is still incomplete
**Status:** Partial / missing key capability in v0.3

## Receipts
- `src/memory/tier3.ts`
  - creates `data/memory.db`
  - defines `memory_entries` with `embedding BLOB`
  - enforces append-only audit rules
- `src/memory/memory-tiers.test.ts`
  - extensive Tier 3 schema and isolation tests exist
- `docs/specs/memory-tiers-spec.md`
  - says Tier 3 storage is SQLite with `sqlite-vec`
  - exact vector index configuration is still TBD
- `docs/ECOSYSTEM.md`
  - `sqlite-vec` is under evaluation / optional feature-flag
- current source survey:
  - no actual `sqlite-vec` extension load / vector index setup / semantic query path identified in current v0.3 source

## Assessment
Tier 3 is no longer missing as a placeholder.
But the stronger claim — semantic/vector memory with actual vector-backed retrieval — is still incomplete.

## Why it matters
Right now Tier 3 looks more like:
- durable structured storage with an embedding column

not yet:
- production semantic memory with real vector indexing/search behavior

---

## 5) Human calibration loop is still incomplete in product form
**Status:** Missing in practice because dashboard is not shipped

## Receipts
- `docs/ARCHITECTURE.md`
  - dashboard is the governance interface through which human calibration is exercised
- `docs/REVIEW_META_PLAN.md`
  - dashboard skill is described as required, not optional
- `docs/ARCHITECT_BRIEF.md`
  - without the dashboard, the human-in-the-loop principle lacks a mechanism
- `docs/specs/dashboard-skill-spec.md`
  - spec exists
- no `src/skills/dashboard/` implementation in v0.3 source

## Assessment
The architecture repeatedly says the calibration loop depends on a real admin-facing dashboard surface.
That surface is still not implemented.

## Why it matters
This is distinct from "some health info exists in TUI." The dashboard is supposed to support:
- KPI trends
- block history
- hansei report review
- calibration decisions
- false-positive capture

That product surface is still missing.

---

## 6) What I am **not** calling missing anymore

Because the receipts do not support those claims as missing in v0.3:

- writable workspace
- session persistence
- compaction hook existence
- stale-session handling
- oversized-session guard (it existed in v0.1 too, with a lower threshold)
- per-group config loading
- TUI health panel basics
- skill registration wire format (`registerSkillScope` / `deregisterSkillScope`)
- provider_type support basics in broker
- Tier 3 storage scaffold itself

Those items may still have runtime bugs, but they are not honestly catalogued as simply "missing in v0.3" based on current source receipts.

---

## Bottom line

After stripping out the unsupported claims, the strongest current missing capabilities in v0.3 are:

1. **No shipped dashboard skill / governance UI implementation**
2. **No call-time enforcement of MCP permission tiers**
3. **No tamper-evident audit-log chain yet**
4. **No full sqlite-vec semantic memory capability yet**
5. **Therefore, no complete productized human-calibration loop yet**

That is a smaller list than the first pass, but it is much cleaner and better supported.
